# 004 — BitNet 1.58 ternary GEMV ({-1,0,+1})

Source: "BitNet b1.58 2B4T Technical Report" (2504.12285); "Bitnet.cpp:
Efficient Edge Inference for Ternary LLMs" (ACL 2025); Ma et al. 2402.17764.
EmergentMind summary: 1.58 bits/weight (log2 3), QAT + STE, custom kernel,
up to 6.25× speedup, lossless vs full precision.

## Core idea
Weights restricted to {-1, 0, +1}. The GEMV inner product becomes additions
and subtractions only — no multiplies. `y[m] = Σ sign-bit · x[k]`. Pack 2
weights per byte (2 trits/byte ≈ 1.58 bits). On a CPU this is dramatically
cheaper than int8 FMA and halves traffic again vs int4.

## Triple-DA
- P1 correctness: ternary multiply is exact integer add/sub; only the *quantization*
(QAT-trained model or post-train ternarize) introduces error. We only apply this
to models we have quantized ourselves or that ship ternary. For a fp32 Qwen we
would ternarize offline (quality cost) — so this is a *format we support*, not a
default for every model.
- P2 privacy: pure bit ops. ✓
- P3 robustness: dequant is exact; the only risk is accuracy of a ternarized model.
  Gate behind an explicit `WUBU_WEIGHT_TERNARY` flag, never auto.

## Implementation plan
- `wubu_gemv_ternary(W_pack, x, y, M, K)`: unpack 2 trits/byte, `y[m] +=
  (t==+1?+x)-(t==-1?x:0)`.
- `wubu_quantize_ternary(W_f32, out_pack, M, K, scales)`: per-block absmax,
  round to {-1,0,+1}.
- Add scheme to `wubu_gemv_autotune` only when caller requests ternary.

## Test oracle
Ternarize a small random matrix, GEMV vs the *ternary* oracle (sign·x) →
bit-exact. Ternarize real Qwen weights, GEMV vs fp32 → report cosine (expected
lower, ~0.9, documents the quality cost). Never auto-enable.
